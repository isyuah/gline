# Gline 后端简历项目文档

这组文档服务于一个明确目标：把 Gline 从“能运行的日志 Agent 加 Server 原型”发展为一个可部署、可演示、可解释、可量化的 Go 后端项目。

文档中的状态词有严格含义：

- **已实现**：当前工作树中存在对应代码。
- **已验证**：本次审计执行过相应命令并得到成功结果。
- **目标设计**：推荐的后续实现，不代表当前已有。
- **验收完成**：不仅有代码，还具备测试、运行证据和文档所列的完成条件。

## 推荐的项目定义

> Gline 是一个面向小型服务集群的自托管日志平台。Go Agent 负责从文件增量采集、解析、批处理与可靠传输；Go Server 负责 API Key 鉴权、幂等接入、持久化和按时间/服务/级别检索，并暴露完整的运行指标与故障证据。

这一定义刻意不把 Gline 描述为 Elasticsearch、Loki 或商业可观测平台的替代品。项目的价值是用可控规模完整展示一个后端系统的关键能力：并发生命周期、协议边界、数据一致性、存储索引、失败恢复、可观测性、性能验证和交付工程。

## 一条主线

后续开发应始终围绕下面这条可演示链路展开：

```text
应用追加日志
  -> Agent 采集并解析
  -> 批次进入持久化 spool
  -> 带幂等键上传
  -> Server 鉴权和校验
  -> PostgreSQL 事务写入
  -> API 按条件分页查询
  -> 指标证明吞吐、延迟、积压和重试行为
```

任何新组件都应回答两个问题：它解决了这条链路中的哪个真实问题，以及如何验证它确实解决了。若回答不了，就暂不引入。

## 当前最短路径

最优先不是微服务拆分、Kafka、Kubernetes 或复杂前端，而是完成以下闭环：

1. 让仓库脱离本机路径后可以独立构建。
2. 固化 Agent 与 Server 的版本化上传协议，并补上真实 HTTP 集成测试。
3. 用 PostgreSQL 替换打印型 Sink，收到成功响应前保证数据已提交。
4. 实现至少一个可用的游标分页查询接口。
5. 加入 API Key 校验、请求限制、超时和优雅关闭。
6. 用 Docker Compose 和固定样例提供一条命令可复现的演示。
7. 再实现幂等重试、磁盘 spool、指标和基准报告。
