# ADR-0001：Server 采用模块化单体

- 状态：建议采纳
- 日期：2026-08-23

## 背景

Gline 当前有 Agent 和 Server 两个天然进程边界。Server 内部未来包含鉴权、日志接入、查询、保留任务和健康/指标。项目目标是形成可部署、可演示的后端闭环，而不是模拟大公司服务数量。

## 决策

Server 在 MVP 和首轮性能验证阶段保持一个进程、一个代码库和一个 PostgreSQL 数据库。内部按 `auth`、`ingest`、`query`、`health` 等能力划分模块，通过窄接口访问 PostgreSQL adapter。

Agent 继续保持独立二进制，因为它部署在数据产生端、拥有本地文件和 spool 状态，生命周期与 Server 本来就不同。

## 原因

- 上传确认和幂等写入可以在一个本地数据库事务中完成。
- 鉴权产生的 project context 不需要跨网络传递。
- 开发、测试和演示组件更少。
- 当前没有独立扩缩容、故障隔离或团队所有权证据支持拆分。
- 清晰包边界已经足以展示架构能力。

## 备选方案

### Ingest、Query、Auth 三个微服务

暂不选择。会引入服务发现、跨服务认证、分布式追踪、部署编排和更多失败模式，却没有改善当前用户场景。

### 所有代码放在 Handler 与 SQL 层

不选择。短期文件少，但协议、业务校验、事务与 HTTP 错误映射会耦合，无法独立测试或平滑拆分。

## 影响

正面：

- 本地 Compose 和集成测试简单；
- 数据一致性边界清楚；
- 迭代速度快；
- 运维成本可控。

负面：

- 接入与查询暂时一起发布；
- 单实例中资源竞争需要连接池、并发限制和指标治理；
- 将来拆分需要把内部调用变为协议。

## 重新评估条件

满足任一条件时重新评估：

- 接入与查询的负载峰值明显不同，需要独立扩缩容；
- 查询拖慢接入且数据库资源隔离无法解决；
- 团队所有权要求独立发布；
- Server 端引入持久化队列后，接入与索引生命周期已经自然分离。
