# ADR-0002：首个持久化后端选择 PostgreSQL

- 状态：建议采纳
- 日期：2026-08-23

## 背景

Gline 既需要追加日志和时间范围查询，也需要 Project、API Key、批次幂等和保留任务。当前没有真实数据证明需要专用列式存储。仓库中虽出现 MongoDB driver 间接依赖，但没有已实现的 Mongo Repository 或必须保持的存储合同。

## 决策

MVP 使用 PostgreSQL 作为唯一 Server 状态存储：

- 关系表保存 Project、API Key 和批次元数据；
- 普通表保存日志 entries；
- JSONB 保存受限动态 attributes；
- 唯一约束与事务实现批次幂等；
- 组合 B-tree 与 BRIN 支持初始查询；
- 达到实测阈值后再评估分区、`pg_trgm` 或 ClickHouse。

## 原因

- 一个事务可以同时提交 batch 和 entries，使 ACK 边界明确。
- 唯一约束天然处理并发重试竞态。
- Query、migration、备份和本地 Compose 工具成熟。
- 对简历项目而言，能够深入解释 SQL、索引和执行计划比浅层接入多个数据库更有价值。
- 目标数据量可以先用实测验证，而不是凭印象假设 PostgreSQL 不够。

## 备选方案

### MongoDB

优点是文档模型与动态 attributes 直观。未选择的原因是批次幂等、项目关系、稳定分页和索引分析在本项目中更适合关系模型；当前也没有既有 Mongo 数据需要兼容。

### ClickHouse

适合高吞吐写入和分析型查询，但会增加元数据存储、轻量更新/删除、测试和本地部署复杂度。作为日志查询存储的演进选项保留，不作为 MVP 前提。

### Elasticsearch/OpenSearch

全文检索强，但资源成本、mapping、集群运维和版本兼容远超当前范围。Gline 的 MVP 查询不需要完整搜索 DSL。

## 影响

正面：事务和幂等设计清楚，部署组件少，查询计划可直接观察。

负面：高基数属性聚合、长期大规模日志和全文搜索可能较弱；保留删除可能产生膨胀，需要 vacuum/分区策略。

## 重新评估条件

- 固定负载下写入吞吐或查询 p95 持续无法达到目标，且 SQL/索引/连接池/分区优化已经验证；
- 数据量和保留周期使 vacuum、索引体积或删除成本不可接受；
- 产品明确需要大量属性聚合或复杂全文检索；
- 有可复现 benchmark 能证明迁移收益大于运维成本。
