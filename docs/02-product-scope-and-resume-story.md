# 02. 产品定位与简历故事

## 1. 目标岗位假设

以下方案默认目标是 Go 后端或基础设施方向的校招、实习、初中级岗位。如果目标是纯业务后端，仍可使用本路线，但应在演示中强化项目/API Key/查询等业务模型；如果目标是可观测性平台岗位，则应进一步强化文件轮转、背压、协议兼容和性能证据。

## 2. 项目定位

### 对用户的定义

Gline 为不想部署完整 Elastic Stack 的个人项目或小型服务集群提供一条简单日志链路：在应用机器上运行 Agent，采集文件中的新增日志，可靠上传到自托管 Server，然后通过 API 按项目、服务、级别和时间范围检索。

### 对简历的定义

Gline 是一个展示后端系统完整性的载体，而不是技术名词集合。它应能用一个可重复演示回答：

1. 数据如何进入系统？
2. 失败时会不会静默丢失或重复？
3. 服务端如何鉴权、校验和持久化？
4. 数据增长后如何查询和保留？
5. 如何知道系统正在积压、重试或变慢？
6. 新机器如何一条命令启动并验证？

### 为什么它比普通 CRUD 更适合作为主项目

| 维度 | 常见 CRUD 项目 | Gline 可形成的证据 |
| --- | --- | --- |
| 并发 | 请求级框架并发 | 多 Pipeline、channel 所有权、取消、排空和 panic 隔离 |
| 一致性 | 单次数据库事务 | 网络超时、重复请求、batch 幂等与 ACK 边界 |
| 状态恢复 | 普通数据持久化 | 文件 checkpoint、磁盘 spool、崩溃恢复和轮转 |
| 性能 | 简单接口 QPS | 接入吞吐、batch 折衷、查询计划和积压恢复 |
| 运维 | 健康检查 | liveness/readiness、背压、重试、retention 和故障注入 |

前提是这些能力真实实现并被验证。日志题材不会自动带来深度；如果没有可靠性、存储和查询闭环，它仍然只是另一个接口原型。

## 3. 目标用户与核心场景

### 目标用户

- 在一到数台服务器上运行 Go、Java、Node.js 等服务的开发者。
- 需要统一查询日志，但不需要大型日志平台全部能力的小团队。
- 希望自托管、资源占用可控、故障语义透明的用户。

### 核心场景

1. 用户为 `orders` 服务配置一个文件 Pipeline。
2. 应用追加 `INFO order created`。
3. Agent 解析并赋予来源信息，形成持久化批次。
4. Agent 用 API Key 上传；网络失败时重试且不生成重复记录。
5. Server 在事务提交后返回确认。
6. 用户查询最近 15 分钟的 `orders + ERROR` 日志。
7. 用户能从指标看到接入量、请求延迟、重试次数和 Agent spool 大小。

三类角色的完整使用体验见[系统全景](./00-system-overview.md)。

## 4. 分阶段定位

项目名称和简历表述应随完成度升级，而不是从第一天就使用最终称谓：

| 阶段 | 可以使用的定位 | 不能声称 |
| --- | --- | --- |
| 当前 | 配置驱动的多 Pipeline Go 日志 Agent 与 Server 接入原型 | 日志平台、可靠投递、可查询 |
| 持久化闭环完成 | 自托管日志采集与查询后端 | 断网/崩溃后不丢、已完成高吞吐验证 |
| 可靠传输完成 | 具备至少一次传输和幂等写入的日志平台 | exactly-once、任意场景零丢失 |
| 可观测与压测完成 | 有故障和性能证据的轻量日志平台 | 超出实测条件的高并发/海量数据 |

这个递进定位也适用于 README：未完成的能力进入 Roadmap，不进入 Features。

## 5. MVP 范围

### 必须完成

- 单个 Agent 支持多个文件 Pipeline。
- `string_line` 解析器可用，解析失败保留原始消息并标为 `UNKNOWN`。
- Agent 批量上传，有明确超时、重试和关闭行为。
- Server 使用真实 API Key 鉴权并绑定项目。
- 上传协议版本化，支持批次幂等。
- PostgreSQL 持久化日志和批次接收记录。
- 查询支持时间范围、服务、级别、关键词和稳定游标分页。
- 请求体、批次、消息、时间范围和分页大小有上限。
- `/livez`、`/readyz` 和 Prometheus 指标可用。
- Docker Compose 可启动 Server 与 PostgreSQL。
- 有 Agent→HTTP→PostgreSQL→Query 的集成测试或演示脚本。
- README 给出五分钟内可完成的本地演示。

### 明确不属于 MVP

- 浏览器日志分析 UI。
- 全文搜索 DSL、聚合分析器和告警引擎。
- Kubernetes Operator。
- 多区域复制。
- 动态 Agent 配置下发。
- Kafka 或自建分布式队列。
- 自研列式数据库。
- “严格 exactly-once” 宣称。

非目标越清楚，项目越容易完成，架构选择也越能自洽。

## 7. 产品验收场景

一个适合录屏和面试现场演示的验收流程：

1. `docker compose up -d` 启动 PostgreSQL 和 Server。
2. 创建或加载一个演示项目及 API Key。
3. 启动 Agent，指向临时应用日志。
4. 连续写入 INFO、WARN、ERROR 和一条无法解析的日志。
5. 查询 API 返回四条记录，来源、时间和级别正确。
6. 暂停 Server，继续写入日志，观察 Agent spool 增长与重试指标。
7. 恢复 Server，spool 归零，查询结果无重复。
8. 重复提交同一 `batch_id`，Server 返回相同确认且数据库行数不变。
9. 使用错误 Key、超大 body、非法级别和超大时间范围，得到稳定的错误码。
10. 展示 `/metrics`、数据库索引计划和一次基准结果。

这十步比展示很多接口更有说服力，因为它覆盖正常路径、失败路径和恢复路径。

## 8. 性能目标的正确写法

性能数字必须来自固定实验，不能先写进简历再补测试。建议先定义目标而不是结果：

| 指标 | 初始目标 | 条件 |
| --- | --- | --- |
| 本地接入吞吐 | 5,000 entries/s | 单 Server、单 PostgreSQL、每批 200 条、固定消息大小 |
| 上传 API p95 | 小于 200 ms | Server 确认前完成数据库提交 |
| 100 万行查询 p95 | 小于 300 ms | 指定项目、15 分钟窗口、服务与级别过滤 |
| Agent 稳态内存 | 有明确上限且随 backlog 不无限增长 | backlog 写入磁盘 spool |
| 网络恢复 | 自动清空积压且不重复 | 固定故障时长和数据量 |

实际测试后记录硬件、操作系统、Go/PostgreSQL 版本、数据分布、并发度、批次大小、完整命令与原始结果。如果未达到目标，应解释瓶颈与下一步，而不是删除失败数据。

## 9. 完成定义

只有同时满足以下条件，才建议在简历中把 Gline 写成“日志平台”而不是“日志 Agent”：

- 克隆仓库后无需本机私有目录即可构建。
- 新环境能按 README 在五分钟左右跑通演示。
- 上传成功等价于数据已持久化或已进入明确定义的持久化边界。
- 网络重试不会制造重复记录。
- 查询 API 能返回刚才写入的日志。
- 核心错误路径有自动化测试。
- 指标足以诊断接入失败、积压和数据库变慢。
- 所有简历数字都有可复现报告。
